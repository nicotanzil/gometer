Guide

Setup, workflows, and measurement reference.

ABOUT TWO MINUTES

Your first test

Start with a small test against the included demo, or a test endpoint you control. Local runs send requests from the machine running GoMeter.

  1. Start a target server

    The demo is a separate program. From a source checkout, run this in another terminal and leave it running:

    ./bin/gometer-demo

    If you use downloaded binaries, run the gometer-demo executable from its folder. The default demo endpoint is http://127.0.0.1:8787/work. Opening the dashboard does not start it.

  2. Prepare a small request

    Use GET, 5 requests per second, a 2-second load window, and a concurrency cap of 2. This plans 10 arrivals. Some may be missed if the generator cannot start them on time.

    Load the practice configuration

    Loads a local GET test with a 1-second timeout, p95 limit of 200ms, and zero allowed errors or missed arrivals. Workers, telemetry, and insecure HTTPS are disabled.

    This replaces your current editor draft. Save your draft first if you need it. Saved scenarios and runs are kept; loading sends no traffic.

  3. Validate the configuration

    Press Validate in the builder. Fix any message before continuing. Validation checks the settings without contacting the target, so it cannot tell you whether the server is reachable.

  4. Start and watch

    Press Start run when you are ready to send traffic. Live run shows activity and final checks. A healthy default demo should complete 10 requests with no request errors or missed arrivals; the latency check still depends on your machine.

    At the end of the load window, admitted work can finish. This is called drain. Stop run cancels active work and saves a partial result.

  5. Read the result before increasing load

    Check the pass criteria, request errors, and missed arrivals together. Save the scenario to reuse it. Increase one setting at a time so you can interpret what changed.

1. Choose the request

Target URL
The complete HTTP or HTTPS endpoint. For the local demo, use http://127.0.0.1:8787/work. In a journey, this becomes the base origin for its steps.
Method, headers, and body
GET usually reads data. POST often submits data. Expand Request settings to add headers and a body; for JSON, add Content-Type: application/json. Use the method and payload your endpoint expects.
Successful status codes
By default, HTTP 200–299 counts as success. Enter a comma-separated list to change that rule. A successful status does not prove the response content is correct; journeys can also assert response values.
HTTPS certificates
Certificates and hostnames are verified by default. The insecure checkbox allows untrusted certificates for workload requests and labels the run. It does not disable worker or telemetry verification.

2. Choose the traffic model

Fixed arrival rate

Choose this when you want a specific offered load, such as 5 new requests every second. Slower responses do not reduce the planned rate.

Example: 5/s for 2 seconds plans 10 arrivals. The concurrency cap limits how many requests, or whole journeys, can be active at once. Arrivals that cannot start are counted as missed.

Concurrent users

Choose this when you want a fixed number of users repeating work. Each waits for its response or journey to finish before starting again, with any configured pause.

Example: 2 users means up to 2 active iterations. It does not mean 2 requests per second; throughput depends on response time and pauses.

Load duration and timeout
2s means two seconds; 200ms means 200 milliseconds. Load duration controls how long new work is admitted. Request timeout bounds each attempt, including its body. Journey timeout bounds the full sequence.
Iterations per user
In Concurrent users mode, choose a stop condition. For example, 10 users × 5 iterations produces 50 request or journey attempts if the run is not stopped early. Failed attempts consume an iteration. With both limits enabled, new work stops at whichever limit comes first; admitted journeys can finish. Pauses occur between iterations, not after the final one.
Startup delay and user ramp
In Concurrent users mode, open Traffic options. Startup delay is a wait before the load duration begins. User ramp-up spaces user starts at ramp × user index ÷ users; for 4 users and 4s, starts occur at 0, 1, 2, and 3s after startup. The ramp is part of the load window. A duration limit can stop the schedule before every user starts. Finished finite users are not replaced.
After a failed request
In Concurrent users mode, open Traffic options. Start next iteration skips the rest of the journey. Continue journey attempts later steps and loop iterations while retaining the failure. Stop this user ends only that user’s future work; peers continue. Stop test gracefully ends the failing journey and drains other admitted journeys; Stop test immediately cancels active requests and journey pauses too. Both cancel pending user starts. Any user or test stopped on error fails the run even with disabled error thresholds. Failed verification publishes no extracted values; journey deadlines and safety limits always abort the journey.
Traffic phases
In rate mode, enable multiple phases for baseline, higher load, and recovery. Phases run in order and set the total duration. Rate 0 pauses new arrivals; admitted work can still finish.
Arrival spacing
Constant spaces planned arrivals evenly. Seeded jitter varies each arrival within its rate interval. It preserves planned demand; it is not a Poisson arrival model.

3. Define a useful pass

Pass criteria turn measurements into a verdict. Choose limits from your application's requirements; the practice values are examples.

Request p95 latency
The histogram estimate of the time within which 95% of completed attempts finish. A 200ms limit allows roughly 5% to be slower. Latency includes the full response and completed failed attempts.
Maximum request errors
Failed attempts divided by completed attempts. 0 means no errors allowed; a blank field disables the check. Failures can include status codes, transport errors, timeouts, or journey assertions.
Maximum missed arrivals
Arrivals missed because of capacity or scheduling delay, divided by scheduled demand. A fast p95 with missed arrivals means the test did not deliver all planned load.
Minimum started HTTP requests / s
A lower bound for actual HTTP attempts started per second over the load window. In a multi-step journey, this counts HTTP attempts, not journeys.

For journeys, these are request checks except missed arrivals, which refers to journey admission. Per-journey checks are in Journey settings & data; test-wide journey checks are in Advanced JSON. Checks needing samples fail when no relevant work was measured.

Read your results

Start with the verdict and checks, then compare the four main measurements.

HTTP attempts / second

Actual attempts started divided by elapsed load time. Compare this with your target for single-request rate tests.

Request latency · p95

How long measured attempts took, including the response body. Missed arrivals have no request latency sample.

Request errors

How much completed work failed. Inspect the run's error categories and checks before changing the load.

Missed workload demand

Planned arrivals that did not start. Check the concurrency cap, arrival delay, and generator resources to investigate.

Requests and journeys have different units. If all steps pass, 10 journeys with 3 steps each produce 30 HTTP attempts. Journey rate targets apply to whole journeys.

Live throughput charts use sample intervals; latency charts and cards use cumulative measurements. Final checks summarize the completed run. Passing the chosen checks does not establish that every response was fast or that the target is healthy under all conditions.

Generator diagnostics describe GoMeter's process. Optional target-server telemetry samples a separate server exporter. Telemetry coverage is reported separately from load checks; gaps are not zeros.

Keep going

Choose a starter
Local smoke test is a small single-request test. JSON request example demonstrates a POST body. Authenticated checkout journeys shows cookies, extraction, and assertions. Branches and loops adds nested conditions and a repeat counter. Baseline, overload, recovery deliberately overloads the default demo and normally fails its checks. Worker and telemetry starters require their respective setup.
Build a journey
A journey is an ordered sequence such as login → profile → checkout. Load the journey starter to open Journey canvas. Select a card to edit its request, checks, or extracted variables. Enable Data flow to trace dependencies; drag cards or use Move up/down to change execution order. Journey settings & data holds weights, variables, datasets, and per-journey criteria. Validate before starting; Preview sequence sends no traffic. Use + Branch or + Loop to add controls, then select them to edit conditions, repeat limits, and child paths. Move to path changes nesting; Undo restores the last edit. A branch runs only its chosen path. A while loop still true at its iteration limit fails the journey. Structure previews show both paths without sending traffic. By default, failed steps stop the journey and later steps are skipped. Concurrent users mode also offers Continue journey, Stop this user, and graceful/immediate test stops under Traffic options.
Use a CSV dataset
In Concurrent users mode, open Journey settings & data → Import CSV dataset. Choose a UTF-8 file with column headers, review the preview and map columns to variable names. Use {{variable}} in a request, with |url, |path or |json where escaping is needed. Shared rows are allocated across users; Each user starts at the first row gives each user their own sequence. Recycle repeats the rows; Stop this user normally ends that user before its next journey. End of data is normal completion and can produce fewer iterations than the configured limit. Saved scenarios include the CSV values.
Save and reuse
Save scenario adds a library entry. Loading it changes the button to Update scenario; use Save editor as a new scenario to keep the original. Run history → Reuse loads the settings from a past run.
Compare two runs
In Run history, select two completed runs with results, then Compare selected. Differences are B minus A. Check warnings about different conditions; a comparison alone does not prove a regression.
Export and import
Editor JSON is reusable configuration. Run + timeline contains configuration and results and can be imported into history. Result JSON and HTML reports cannot be imported as run bundles. Configuration exports and bundles include supplied headers, bodies, and data; review them before sharing.
Workers and telemetry
Choose This machine for a first local test. Use the Workers view to register named generators, then Build → Execution & diagnostics → Selected workers to choose them. Connection checks are manual observations; starting a run checks every worker again. Catalog edits do not change existing configurations or run history. Workers split the configured fleet rate; they do not multiply it. Each worker must reach the target URL; localhost on a remote worker means that worker’s machine. Server telemetry needs an existing Prometheus text exporter and exact metric selections. Neither is required to run a test.
BRING YOUR EXISTING TEST

Import from JMeter

In Build, choose Import JMeter JMX, then upload a .jmx file or try the HTTP sample. Importing sends no workload traffic and keeps your builder draft until you choose to open a saved scenario.

  1. Review compatibility

    Select each component for its mapping and source path. Supply required property values and press Apply values. The first converter targets a limited set of JMeter 5.6.3 HTTP plans; scripts, CSV files, multiple groups, unknown failure actions, redirects, and other unsupported behavior block conversion. Finite iterations, standard ramps, and all five standard failure actions are supported, with explicit runtime differences.

  2. Review runtime policies

    GoMeter uses a 5s total request timeout, 30s journey deadline, 10 MiB response limit, verified HTTPS, and its own reports. Connections, default headers, cookies, and measurements may differ. Accepting these policies does not bypass component blockers.

  3. Preview and save

    Compatible plans show a read-only journey canvas. Save scenario puts a runnable native configuration in the Scenario library. Save migration draft preserves a blocked plan below that library, where it cannot run. Fix source blockers in a copy of the JMX and choose the revised file.

  4. Run separately

    Open a saved scenario in the journey builder to edit or run it. Start run is the action that sends traffic. For the sample, start the bundled demo on port 8787 first. Review original JMX shows the retained source, which may differ from later builder edits.

When something goes wrong

Validate passed, but the requests fail

Validation checks settings without contacting the target. Confirm the server is running, the URL and port are correct, and the endpoint is reachable from the machine running GoMeter. For the demo, start gometer-demo separately on port 8787.

My development HTTPS server has an untrusted certificate

Use a certificate trusted by the GoMeter machine, or explicitly select Skip HTTPS certificate verification (insecure) in Request settings for that workload. The run will be labeled. Worker and telemetry HTTPS still require their own valid trust configuration.

Latency looks fine, but arrivals are missed

Latency measures work that ran. Missed arrivals did not get a latency sample. Inspect capacity and scheduler misses, arrival delay, and generator resources. Reduce the rate to establish a baseline; raise concurrency only when the generator and target have room.

The run failed even though HTTP responses succeeded

Read the failed checks. A latency limit, missing demand, minimum throughput, or whole-journey timeout can fail independently of HTTP status. A journey assertion can also fail a response with status 200.

Start run is disabled

The dashboard allows one active run. Open Live run and View active run if shown. Wait for it to finish, or use Stop run to cancel it and save partial results. CLI processes started separately are independent.

I closed the browser, or stopped a run

Closing the browser does not stop a test while the dashboard process stays running. Reopen the dashboard to reconnect. Stop run cancels active work and saves an interrupted result. A process that ends before final persistence leaves an abandoned run that cannot be resumed or compared.

My imported JSON is rejected

Unknown fields, invalid values, and trailing JSON are rejected. Use editor JSON for a configuration and Run + timeline for a saved run. CLI result JSON has no configuration and cannot be imported as a run bundle. Configuration files are limited to 1 MiB; run bundles to 16 MiB.

Capability comparison

Development sequence

  1. HTTP workflows: data files, richer correlation and assertions, authentication, redirects, uploads, and recording.
  2. Execution controls: loops, conditions, shared fragments, setup/teardown, user ramps, timers, and bounded debug samples.
  3. Protocol adapters: databases, messaging, TCP, LDAP, file transfer, mail, and Bolt, each with an integration fixture.
  4. Compatibility & extensions: scripting, component APIs, scoped JMX migration, JTL exchange, and conformance tests.
  5. Beyond parity: WebSocket, gRPC, OpenTelemetry export, and repeatable regression analysis.
